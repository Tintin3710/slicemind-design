# 금액 변경과 최종 확인 패턴

패턴 ID: P-AMOUNT-01 · 버전: v2.1 (2026-10-29, ‘시각적 구성’ 추가) · 상태: 기존 판단을 사후 정리한 재현 실험용 규칙

v1(커밋 `928d97d`)은 간병비 조정 기준으로 작성했다. v2는 같은 구조를 환불 등 다른 금액 흐름에도 쓸 수 있도록 일반화했다. 기능별 조건(인상률·평일/주말 단가·재신청 문구 등)은 각 기능 문서에서 관리한다. 간병비 조정에 적용한 예시는 [price-adjustment](features/price-adjustment.md#공통-패턴-적용)에 있다.

## 목적과 적용 조건

사용자가 금액을 바꾸거나 결제·환불처럼 금액이 오가는 행동을 하기 전에 그 영향과 최종 결과를 이해하도록 돕는다. 간병비 조정·재신청에 먼저 적용했다. 결제·환불에 적용하는 것은 각 기능에서 따로 검증한다.

## 결정의 근거

| 관찰·판단 | 규칙으로 남길 내용 |
|---|---|
| AI 초기 시안은 여러 정보를 한 단계에 모아 핵심 입력을 밀어냈다. | 각 단계의 핵심 질문과 직접 관련된 정보부터 보여준다. |
| 정보를 줄이자 선택의 영향이 총금액 안에 묻힐 수 있었다. | 정보량만 줄이지 않는다. 판단에 필요한 값은 선택·조건 가까이에 둔다. |
| 같은 조건도 항목마다 금액 변화가 다를 수 있다. | 항목별 변경 전후나 계산 근거를 함께 보여준다. |
| 상세 합산 내역은 최종 행동 전에 확인하면 된다. | 선택·확인 단계와 최종 확정 단계의 역할을 나눈다. |

이 근거는 설계 판단이다. 실제 사용자가 더 안심했다거나 과업 성공률이 올랐다는 결과는 별도 검증이 필요하다.

## 규칙

| ID | 규칙 | 필요한 이유 | 확인할 것 |
|---|---|---|---|
| P01 | 선택이 있는 화면에서는 선택 UI를 가장 먼저 식별할 수 있게 한다. 선택이 없는 금액 확인 화면에서는 적용 조건(예: 취소 시점, 적용 기준)을 먼저 보여준다. | 화면의 핵심 질문에 바로 답하게 한다. | 선택 UI 또는 적용 조건의 위치 |
| P02 | 선택이 있으면 선택 결과(항목별 변경 전후, 최종 금액)를 선택 UI 가까이에 보여준다. 선택이 없으면 적용 조건·계산 근거·최종 금액을 함께 보여준다. | 선택이나 조건이 금액에 미치는 영향을 바로 확인한다. | 선택·조건과 금액의 거리 |
| P03 | 최종 행동 전에 포함 항목·차감 항목과 계산 근거를 확인할 수 있게 한다. | 확정 전에 금액의 근거를 확인한다. | 최종 확정 화면의 상세 내역 |
| P04 | 버튼 문구는 누른 뒤 실제로 일어나는 일을 설명한다. 이동(예: ‘변경 금액 확인하기’, ‘취소 사유 선택하기’)과 최종 확정(예: ‘{금액}원으로 ○○하기’)을 구분한다. | 어느 단계에서 확정되는지 알 수 있게 한다. | 단계별 버튼 문구 |
| P05 | 금액의 의미는 라벨로 전달하고 색은 보조로만 쓴다. 강조 역할은 아래 ‘금액 강조 역할’을 따른다. | 색만으로는 결제·환불·위약금의 의미가 전달되지 않는다. | 라벨 유무, 색과 라벨의 일치 |
| P06 | 한 기능의 화면·상세·버튼은 같은 계산 결과를 사용한다. 계산 정책(간병비, 환불 등)은 각 기능에서 따로 관리하고, 공통 UI는 계산하지 않고 결과만 받는다. | 화면마다 금액이 달라지는 오류를 막는다. | 기능별 단일 계산 경로, 공통 UI의 계산 의존성 |
| P07 | 검토와 뒤로 가기만으로는 거래 상태를 바꾸지 않는다. 최종 확정 버튼만 상태를 바꾸고, 확정하지 않고 나가면 기존 상태를 유지한다. 검토 중·요청 접수·처리 완료는 구분해 표현한다. 확정 전에는 ‘예상’ 금액, 확정 후에는 ‘적용’ 금액처럼 라벨을 바꾸고, 확정 버튼은 완료 상태 문구로 바꿔 비활성화한다. 완료 안내는 한 번만 보여준다. 요청 접수(예: 취소 접수)를 처리 완료(예: 환불 완료)로 표현하지 않는다. | ‘확인’만 했는데 금액이나 거래가 바뀌는 일, 처리 중인 일을 끝났다고 오해하는 일을 막는다. | 이동·닫기·확정 후의 상태, 단계별 라벨·버튼·안내 문구, 완료 안내 중복 |

## 금액 강조 역할

정확한 색 값은 [design-system](design-system.md)의 대응표와 토큰을 따른다. 색은 항상 라벨과 함께 쓴다.

| 금액의 의미 | 라벨 예 | 강조 역할 | 토큰 |
|---|---|---|---|
| 예상 결제·적용·환불 예정 등 사용자가 받거나 낼 최종 금액 | ‘예상 결제 금액’, ‘환불 예정액’ | accent | `color.text.accent` |
| 위약금 발생 표시와 위약금 금액 | ‘위약금 발생’, ‘위약금’ | negative | 사용자 지정 `color-semantic-status-negative` (= 실제 `palette.error.main`, design-system 참조) |
| 위약금 없음 등 해당 금액이 없음 | ‘위약금 없음’ 또는 금액 자리에 ‘없음’ | neutral | `color.text.primary` |
| 일반 상세 항목 | 항목명 | default | `color.text.primary` |

일반 인상률이나 결제 금액 전체를 negative로 표시하지 않는다.

## 좋은 예시와 피할 예시

| 좋은 예시 | 피할 예시 |
|---|---|
| 선택 바로 아래에 항목별 변경 전후와 최종 금액을 보여준다. | 항목별 차이를 하나로 뭉뚱그리거나 총금액만 보여준다. |
| 선택·조건을 먼저 확인하고, 최종 확정 화면에서 포함·차감 항목을 확인한다. | 입력 위에 모든 비용 내역을 펼쳐 핵심 입력을 밀어낸다. |
| 이동 버튼 다음에 금액이 명시된 확정 버튼을 둔다. | 두 단계 버튼이 모두 같은 확정 문구여서 어디서 확정되는지 불명확하다. |
| ‘가능성을 높일 수 있어요’처럼 가능성으로 안내한다. | 근거 없이 결과를 보장한다. |
| 확정 후 금액 라벨을 ‘적용 금액’으로 바꾸고 버튼을 ‘○○ 완료’로 비활성화한다. | 완료 후에도 ‘예상’ 라벨과 확정 버튼 문구를 그대로 두거나, 같은 완료 금액을 여러 곳에 반복한다. |
| 취소 요청 후 ‘취소가 접수됐어요’라고 안내한다. | 환불이 처리되기 전에 ‘환불이 완료됐어요’라고 안내한다. |

## 토큰과 컴포넌트의 역할

- 토큰: 금액·본문·구분선·주요 행동을 어떤 시각적 의미로 표현할지 정한다. 계산식이나 위약금 비율은 담지 않는다.
- 공통 컴포넌트(`AmountSummary`, `PriceChangeRow`, `StatusBadge`): 라벨·금액·강조 역할을 props로 받아 표시만 한다. 기능별 계산 파일에 의존하지 않는다.
- 이 패턴: 그 컴포넌트를 **언제, 어디에, 어떤 정보와 함께** 사용하는지 정한다.

## 시각적 구성

- 최종 금액은 `AmountSummary`, 금액 관련 상태 표시(예: 위약금 발생·없음)는 `StatusBadge`를 사용한다. 변경 전후 금액은 `PriceChangeRow`를 사용한다.
- 상세 내역은 항목명을 왼쪽, 금액을 오른쪽에 정렬한다. 현재 스타일 기준은 간병비 확인 화면의 `DetailLine`(`src/screens/guardian/price-adjustment/screens.tsx`)이다. `DetailLine`은 공통 컴포넌트가 아니라 화면 내부 구현이다.
- 카드와 정보 그룹 사이의 간격은 `semantic.space`(`src/design-system/token-bridge.ts`)의 `related`·`row`·`section`을 따른다.
- 기능마다 라벨·금액·강조 역할(위 ‘금액 강조 역할’)만 바꾸고, 공통 컴포넌트의 시각 스타일은 그대로 유지한다.

## 다른 흐름에 적용할 때

결제는 결제 총액과 포함 항목, 환불은 차감 항목과 환불 예정액을 확정 전에 보여준다는 구조를 공유한다. 결제액·환불액·위약금은 의미가 다르므로 카드 모양이 같아도 라벨·강조 역할·확정 동작은 기능별로 정한다. 환불 정책과 예시 금액은 [cancellation](features/cancellation.md)에서 정하며 이 문서에 넣지 않는다. 환불 흐름의 구현과 검증은 현재 미실행이다.
